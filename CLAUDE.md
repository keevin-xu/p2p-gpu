## What this project is

A volunteer-compute grid that runs GPU workloads across browser tabs via **WebGPU**. A C++ coordinator schedules work across heterogeneous, unreliable, untrusted worker nodes; workers run WGSL compute kernels and return results. Bulk assets are distributed peer-to-peer over WebRTC so coordinator egress stays flat as the fleet grows.

**The entire system is C++20.** One `worker-core` library compiles to both a native binary and a WebAssembly module, so the browser worker and the native worker are the same code against the same WGSL kernels. There is no TypeScript, no second language, and no cross-language codegen.

This is a **resume/portfolio project optimized for demonstrable distributed-systems depth**. The deliverable is not just working code — it is working code *plus the measurements in `docs/EVALUATION.md`*. A feature that cannot be measured is lower priority than one that can.

Full background and the physics that constrain the design: **`RESEARCH.md`**.

## THE HARD RULES

These are non-negotiable. If a task appears to require violating one, **stop and ask the human**. Do not work around them.

### R1 — Dumb worker, smart coordinator
The worker executes tasks and reports facts. It makes **no decisions**. All scheduling, task sizing, validation, reputation, and retry logic lives in the coordinator. Keeping the worker thin is what keeps `worker-core` small enough to be confidently correct on two very different targets.

### R2 — One `worker-core`, two targets. Never fork it.
`worker-core` compiles to native and to WebAssembly from **identical source**. Platform differences are handled with narrow `#ifdef __EMSCRIPTEN__` seams inside dedicated files, never by duplicating logic. If you are about to write the same algorithm twice for the two targets, stop — that is the mistake this rule exists to prevent.

### R3 — The protocol has exactly one definition
`protocol/p2pgpu.fbs` is the single source of truth. C++ headers are **generated by `flatc` at build time** into the build directory. Never hand-edit generated code, and never define a wire type outside the schema.

### R4 — No single GPU dispatch may exceed 250 ms of expected work
Windows TDR kills GPU work blocking ~2 s and resets the driver; the browser surfaces this as a lost device. Long tasks are implemented as **many short dispatches with yields between them**, never one long kernel. Every worker must handle device loss and re-acquire.

### R5 — Every workload must clear the arithmetic-intensity gate
Before adding any new kernel, compute its FLOP-per-output-byte. It must exceed **10⁶**, or be redesignable to exceed it via on-node accumulation. Document the calculation in `docs/DECISIONS.md`. A workload below this bar is transfer-bound and adding nodes will not help. See `RESEARCH.md` §2.

### R6 — Never assume GPU float results are bitwise reproducible
Honest nodes on different vendors/drivers disagree in the last few ULPs (FMA contraction, fast-math, differing transcendentals). Verification must use the kernel's declared `DeterminismClass` (`Exact` / `Tolerant(eps)` / `Statistical`). Bitwise comparison is only valid for `Exact` (integer) kernels.

### R7 — Explicit opt-in, always
No GPU work begins without an affirmative user click. The worker page must show a visible "contributing" indicator, a user-settable throttle, and an instant stop control. This is a hard requirement from day one, not a polish item. (See the Coinhive case in `RESEARCH.md` §4 — silent background compute gets domains blacklisted.)

### R8 — Tasks are leased, not assigned
A worker disappearing mid-task is the **normal** case, not the exceptional one. Every task has a lease with an expiry. Unrenewed leases return to the queue automatically. There is no code path that assumes a worker will come back.

### R9 — Log the decision before you implement it
Any choice matching the criteria in `docs/DECISIONS.md` gets an entry appended **before** the implementing code is written. See that file for the full rule set.

### R10 — Do not cross a roadmap gate without human approval
`docs/ROADMAP.md` defines phases separated by `HUMAN GATE` blocks. When you reach a gate, stop, produce the gate's required evidence, and wait. Do not begin the next phase.

### R11 — Nothing reaches program logic without passing the Verifier
The coordinator's entire input surface is attacker-controlled: anyone can connect as a worker. Therefore:

- **All deserialization goes through `flatbuffers::Verifier`.** A buffer that fails verification is dropped before any field is read. No exceptions, no "this path is internal."
- **No raw pointer arithmetic, `memcpy`, or C arrays in any code that touches network bytes.** Use `std::span`, `std::string_view`, and bounds-checked accessors.
- **Validate every length field against its MAX constant before allocating.** FlatBuffers prevents memory corruption; it does not prevent an attacker OOM-ing you with a declared 4 GB payload.
- **ASan + UBSan builds run in CI. Fuzz harnesses run in CI. The corpus is committed.**

This rule is why C++ is defensible for this project. See `docs/DECISIONS.md` D-0010.

## Stack

| Layer | Choice |
|---|---|
| Language | **C++20** everywhere |
| Build | CMake ≥3.25 + CMakePresets, vcpkg manifest mode |
| Wire format | **FlatBuffers** — schema-driven, `Verifier` for untrusted input (R11) |
| Coordinator HTTP/WS/SSE | uWebSockets |
| Worker transport | libdatachannel (native) / datachannel-wasm (browser) — **same API both targets** |
| WebGPU, native | wgpu-native (prebuilt, implements `webgpu.h`) |
| WebGPU, browser | `--use-port=emdawnwebgpu` (Dawn's `webgpu.h`). **Not** `-sUSE_WEBGPU`, removed in Emscripten 6 — see D-0014 |
| Persistence | SQLite (not Postgres, not Redis — do not add them) |
| Logging | spdlog |
| Testing | Catch2 v3 · libFuzzer · ASan/UBSan/TSan |
| CLI | CLI11 |
| Kernels | WGSL |

Rationale for the language choice is in `docs/DECISIONS.md` **D-0008** (supersedes D-0004). Short version: one language across every component including the browser, made possible because libdatachannel/datachannel-wasm expose one WebRTC API to both targets — the exact gap that made a single-language stack impractical in other languages.
