# Phase 5 — Workload A: Distributed Path Tracer

**Objective:** the visually demonstrable workload, and the empirical test of the project's central thesis — that on-node accumulation keeps distributed nodes compute-bound.

**Why now:** biggest kernel effort, needs accumulation infrastructure, and produces the large asset (scene BVH) that justifies Phase 6's P2P data plane.

**Entry criteria:** G4 approved.

> This phase tests D-0001 empirically. If utilization comes in low, that is a **finding to report**, not an experiment to tune until it agrees (`RISKS.md` R-A).
>
> Mac-only development is fine for this entire phase (`RISKS.md` R-D hardware plan). No borrowed hardware needed until Phase 7.

---

## Steps

### R5 gate first

- [ ] **5.1 — Do the arithmetic-intensity calculation before writing WGSL.**
  Per `KERNELS.md` §1. Naive per-tile rendering fails (~6.3e4, 16× short). Show that accumulation to the chosen sample count clears 10⁶. Record the required `min_iterations` — **derived, not guessed** — as it sets the accumulation policy.
  `DECISIONS.md` entry.

### Scene & BVH

- [ ] **5.2 — Scene format + generator script.**
  Simple scene description (spheres/triangles, materials, camera). Generated by a script — no large committed binaries (`CONVENTIONS.md` §11).

- [ ] **5.3 — BVH construction (coordinator-side).**
  Build once, serialize to a GPU-friendly flat layout, content-hash with BLAKE3. This becomes the `input_ref` asset and, in Phase 6, the thing worth distributing peer-to-peer.

- [ ] **5.4 — Asset serving.**
  `GET /asset/{hash}` on the coordinator; worker-side content-addressed cache. The fallback path Phase 6's P2P plane sits in front of (D-0007).

- [ ] **5.5 — Verify assets on load, always.**
  Even coordinator-served assets get their BLAKE3 hash checked before parsing, and the flat BVH layout is bounds-validated before any traversal index is used. In Phase 6 this same path will accept peer-supplied bytes; build it hostile-ready now rather than retrofitting (R11).

### Kernel

- [ ] **5.6 — `pathtrace_tile.wgsl`.**
  BVH traversal, diffuse + specular materials, cosine-weighted importance sampling, Russian roulette termination. Params: tile coords, camera, sample range, seed.

- [ ] **5.7 — Counter-based RNG (K2).**
  Seeded from `(task_seed, pixel_index, sample_index)`. **Critical:** a given (tile, sample range) must produce identical samples on any device, or replication and speculation are unsound.

- [ ] **5.8 — Accumulation buffer.**
  Persistent GPU buffer per tile holding running sum + sample count. Each dispatch adds samples; never reset mid-task.

- [ ] **5.9 — Chunked dispatch with accumulation (R4/K1).**
  Many ≤250 ms dispatches accumulating into the same buffer, yielding between. Upload the running *average* on `upload_interval_ms`, not every dispatch.

- [ ] **5.10 — Manifest entry.**
  `determinism = "statistical"`, `accumulates = true`, `min_iterations` from 5.1, full R5 fields.

- [ ] **5.11 — Params parity `static_assert`.**
  C++ struct vs. WGSL layout, field for field (`CONVENTIONS.md` §5). The path tracer's params struct is large enough that drift is a real risk.

### Host + coordinator

- [ ] **5.12 — Accumulation host logic in `worker-core`.**
  Written **once**; both targets get it for free (R2). Partial uploads carry an incrementing sequence so the coordinator can order them.

- [ ] **5.13 — Partial-result handling.**
  Coordinator accepts multiple partial uploads per task, each superseding the last. A task's contribution is its most recent upload. Lease renewal tied to upload cadence.

- [ ] **5.14 — Statistical comparator (completes 3.1).**
  Two honest workers rendering the same tile with different sample counts produce *different but statistically consistent* images. Implement a variance-aware consistency test. Do **not** use a fixed pixel-difference threshold — it will either miss real cheating or flag honest noise.

- [ ] **5.15 — Tile decomposition + compositing.**
  Coordinator decomposes the image into tiles, tracks per-tile accumulated samples, composites the current image, serves it to the dashboard.

- [ ] **5.16 — Progressive display.**
  Dashboard shows the image refining live as samples accumulate and workers join. This is the demo.

- [ ] **5.17 — Sample-budget scheduling.**
  Prefer granting tiles with the fewest accumulated samples so the image converges evenly rather than in patches.

- [ ] **5.18 — Activate cache affinity (from 2.16).**
  Now that a real asset exists, prefer granting tiles to workers already holding the BVH. Measure the hit rate.

### Verification & experiments

- [ ] **5.19 — Single-machine reference render.**
  High-sample-count reference from `worker-native` standalone. Ground truth for correctness.

- [ ] **5.20 — Distributed vs. reference comparison.**
  Must match within stated tolerance. Report the metric used (RMSE or similar) and the value.

- [ ] **5.21 — E2 utilization measurement.**
  `gpu_ms` / `transfer_ms` / `idle_ms` breakdown. **Target ≥85% GPU.** Run under `native-release` — never under sanitizers (`CONVENTIONS.md` §8).

- [ ] **5.22 — E2 control run: accumulation disabled.**
  Same job with `min_iterations = 1` (upload every dispatch). Should show low utilization, empirically demonstrating the D-0001 thesis.
  **The pair of bars from 5.21 and 5.22 is the most persuasive chart in the project** — do not skip the control.

- [ ] **5.23 — Demo capture.**
  GIF/video of the image converging as workers join and leave.

## Deliverables

- Path tracer kernel with accumulation, R5-documented
- BVH construction + content-addressed, hash-verified asset serving
- Statistical comparator
- Progressive tile compositing and live dashboard display
- Reference-render correctness verification
- E2 utilization charts, with and without accumulation
- Demo capture

## Exit criteria

1. Image converges visibly as workers join; matches the reference within stated tolerance
2. R5 calculation shows accumulation clears 10⁶, with the derived `min_iterations`
3. Measured utilization ≥85% GPU time
4. Accumulation-disabled control run shows the contrast
5. Statistical comparator produces zero false positives on honest workers with differing sample counts
6. Assets hash-verified and bounds-validated before traversal
7. Cache-affinity hit rate measured
